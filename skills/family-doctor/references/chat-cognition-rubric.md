# 聊天认知观察：逐维执行规则

本规则供 Hermes 当前模型分析真实的自然交流，帮助家人发现值得核实的变化。它不是临床量表、诊断标准或经过验证的痴呆筛查算法。不要计算患病概率、解释为确诊，或把模型置信度作为疾病风险。

## 先做来源与质量核对

1. **分清谁在说、说的是谁。** `self` 是成员本人原始表达；`caregiver` 是家属对另一成员的观察。家属语法、记忆和措辞不能成为被代述者的语言样本。共用账号、转发、引用、AI 改写或来源不明的文本不能冒充本人。
2. **保留输入方式。** `text` 与 `voice` 分开比较；语音转写有错、断句不可靠或可能听错时标记 `asr_uncertain`，不要把识别错误判为找词困难。只有转写文字时不能推断语速、停顿、口音或声音变化。
3. **检查观察条件。** 睡眠不足、疲劳、情绪、药物、听视力、问题不清楚、上下文截断、AI 误解等均可能改变交流。已知的因素按约定枚举填写；不知道不能写成“已排除”。
4. **只使用窗口中的原始用户表达。** 助手文本只能提供问题/回答的先前上下文；不能作为用户认知变化证据。转述必须保持家属来源。不要查找其他成员聊天或将一般病历拼成原始对话。
5. **先检查急性情况。** 若原话显示突然出现明显混乱、定向变化等，当轮正常安全回应优先；不等待观察累计，也不让“仅 Web 提醒”的设置压掉必要的紧急就医协助。

家属在不同日期再次讲述同一次历史事件，不是老人又发生了新变化。若只是复述旧事，使用 `not_current`，实际发生日期无法核实时保留资料不足；不能把插件接收时间解释成症状时间，或累计成三个新的独立日期。只有明确报告另一日期真实新发生的情况，才可能成为新的家属观察；普通澄清、更新背景与消息重发不增加异常次数。

不足两个用户消息或不足三条总消息时，工具自动将窗口作为上下文受限。不要为了通过门槛复制消息、编造问题、补造时间或暗中测试用户。

## 每个维度的判定步骤

全部九个维度都要检查，但不要求每个维度都存在可判断机会。先定位一个真实的回应机会，再比对先前上下文与用户回应，最后检查反例和其他解释。

- `not_assessable`：没有合适机会，或证据不足。保持空机会列表，不将“未出现相关话题”填为正常。
- `no_signal`：在一个具体可判断机会中，用户的回应能够衔接相应要求。仅代表该机会没有观察到本维度线索，不表示认知正常。
- `possible_signal`：在具体机会中存在需核实的变化线索，并有用户原句与必要上下文支持。不是疾病结论；不确定含义时宁可保留不足，不根据年龄、语气或篇幅打标签。

每个机会填写 `response_ids`、必要的 `context_ids`、`outcome` 和 `evidence`。`evidence` 的 `quote` 必须是被引用用户消息的精确连续子串，不能改写、拼句、纠错后引用或引用助手文本。引用尽量短，仅覆盖支持该机会的表达；`context_ids` 必须早于对应回应。前四维必须有先前上下文引用，后五维可以使用一个用户消息中的明确自述/家属观察线索，但整个窗口仍须满足质量条件。单个机会不要囊括大量无关用户消息来增加分母。

## 九个维度：看什么、怎样区分

| 维度 | 可判断的真实机会与可能线索 | 必须检查的反例与限制 |
|---|---|---|
| 重复提问 `memory_repetition` | 当前上下文已经明确回答同一实际问题，用户随后再次提出同一问题，且不像要求核对、补充或更正。以先前回答及后续原句组成机会。 | 消息重发、网络重试、助手漏答/答错、回答太长、没听清、对安排不放心而确认、主动强调都不能直接算忘记。相似用词但问不同对象/时间是不同问题。 |
| 上下文记忆 `context_memory` | 交流确实依赖刚刚提供的可理解信息；用户随后明确忘记、混淆或无法延续。区分对话所需的近时信息与其他长时记忆。 | 助手未说明、信息过载、对话间隔长、被打断、话题切换、没有看到消息，不等于记忆下降。不能自行设计记词、倒数等隐藏测试。 |
| 理解回应 `comprehension` | 一个清楚、单一、符合当前话题的问题后，回应持续无法对应问题，或明显误解核心要求。先审查问题本身是否清楚。 | 中文省略、方言、幽默、礼貌回避、不愿回答、听视力/转写问题、助手错误假设、一次误会都可能解释回应；不配合不是认知损害。 |
| 话题连贯 `coherence` | 用户在同一自然叙述中多次失去必要衔接、因果或指代，使真实意思难以跟随；必须结合前文。 | 正常换话题、口语跳跃、简短回答、故事插叙、多任务、聊天软件分条发消息，不构成连贯困难；不能用标点、错字或句长直接判断。 |
| 时间顺序 `temporal_order` | 用户描述真实事件先后时出现无法解释的矛盾、前后颠倒，或明确表示无法整理顺序。 | “昨天/上次”参照不清、跨午夜、时区、不同事件混在一起、日期口误、回忆大致时间，先核实；不要把消息接收时间当症状发生时间。 |
| 找词表达 `word_finding` | 原话明确显示反复找不到熟悉词、反复绕述而无法命名，或用户/家属明确描述近期找词变化。 | 单个错字、输入法选词、不会专业术语、方言/第二语言、教育差异、语音识别误差和偶尔“那个”不足以下结论。仅文字不能测量真实停顿。 |
| 时间地点定向 `orientation` | 原话明确表示不清楚自己身处何地、日期/时段等，或可核实背景中出现显著不一致。 | 玩笑、假设、旅行、不同地点、时区、日期口误或问路本身不是定向障碍。没有可靠实际背景时不把猜测填成异常。突然变化单独检查急性证据。 |
| 计划组织 `planning` | 在真实日常任务中，明确难以安排熟悉步骤、持续遗漏关键顺序，或报告与以往相比执行困难。 | 不熟悉手机/新软件、任务过难、缺资源、身体不便、别人替办出于便利，与认知相关执行变化不同。聊天模型不能据此测量正式执行功能。 |
| 日常功能 `daily_function` | 用户或家属明确描述原本能独立完成的日常活动现在需要帮助，须保留实际任务与变化背景。 | 既有长期分工、暂时外伤、行动障碍、不愿做、照护者主动接管、收入/环境变化都可能解释；一次忘带物品不能直接宣布生活能力下降。 |

不同维度可以引用同一条消息，但每维同一回应只计算一次。多维命中不表示多个独立事件，也不自动提高疾病等级。分析可以在模型上下文中考虑多种解释，保存只能使用规定的枚举、机会和原句证据；不要加入自由文本“诊断报告”或推理长文。

## 急性变化与提醒边界

`urgent.status=possible_acute_change` 需要同时有变化证据和突然/近期急性起病的用户原句证据；`reason_codes` 仅允许 `sudden_confusion`（突然明显意识/定向变化）或 `sudden_function_change`（突然明显日常功能变化）。不要因普通忘词、长期旧病、引用的故事、假设情景或“老年痴呆”关键词而标记急性变化；缺少起病依据保持不确定，不自造原因代码。`status=none` 时原因与两组证据都为空。

认知变化的聚合提示只在 Web 展示；不要调用飞书发送工具、主动给老人发送认知风险提醒，也不要在普通回复、过程说明或附件中发布分析报告。用户直接询问是否存在观察功能或如何处理其信息时如实解释。对真实的突然意识混乱等急症，当轮仍应提供必要的安全与就医协助，这与常规认知统计通知是不同的任务。

## 医学依据与工程限制

NICE 的评估建议要求结合本人及熟悉其情况者提供的信息，关注认知与日常生活变化，并调查其他可能原因；这里据此设计来源区分与影响因素记录，并没有把上述九维变成经过验证的临床量表。[NICE NG97](https://www.nice.org.uk/guidance/ng97/chapter/Recommendations)

NHS 说明突然意识混乱可能有多种需及时处理的原因，应尽快寻求医疗帮助；不要把急性变化自动解释成痴呆进展。[NHS：突然意识混乱](https://www.nhs.uk/symptoms/confusion/)

本规则的“机会”“重复天数”和 Web 复核门槛是工程约定。软件验证只能核对格式、引用存在、来源与计数，不能证明模型解释正确；需用经人工复核的真实适用场景评估误报、漏报和方言/教育/输入方式差异后，才可判断其实际价值。
